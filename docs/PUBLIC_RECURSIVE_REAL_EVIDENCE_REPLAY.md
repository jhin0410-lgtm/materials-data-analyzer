# Public-API real-evidence recursive replay

This document records the scope and scientific boundary of the public recursive replay added for issue #203.

## What the replay demonstrates

The acceptance path exercises the supported public facade at `materials_data_analyzer.research_loop.public_recursive_api` through two deterministic cycles:

1. an audited reference-heat execution is deliberately run with an unrealistically strict numerical tolerance so the repository-pinned solver verifier produces a real `numerical_validation_failed` outcome;
2. the discrepancy layer represents that failure as `numerical_invalidity` while explicitly recording that no empirical artifact exists;
3. the policy/planning layer translates only that diagnostic action class from `numerical_validation` to the executable planner category `simulation`, without asserting availability or authority;
4. the fresh planner candidate is reconstructed from the live typed heat request, action registry, research state and existing planning adapter;
5. the public recursive checkpoint binds the source discrepancy SHA, objective, selected candidate, predecessor context and immutable recursive limits;
6. the corrected heat action is executed through the existing explicit typed authorization/request/executor chain and independently reconstructed from the immutable ledger, exact request, registry and repository-pinned domain verifier;
7. a repository-pinned heat transition verifier publishes a narrow computational verification decision, after which the authenticated epistemic-transition consumer applies only diagnostic graph edges;
8. the evaluated graph is refreshed and a second discrepancy is built. Numerical validity now passes, but the absence of empirical evidence remains explicit as `empirical_evidence_not_acquired`;
9. fresh second-cycle planning requests `external_evidence_search` but may not invent a candidate. The exact registry pinned by the preceding execution request is reloaded and scanned. A bounded stop is accepted only when that exact registry contains zero currently available external-evidence actions;
10. the replay manifest reconstructs cycle-1 progression and re-diagnosis completion, binds the exact progression SHA into the completion, proves that the cycle-2 handoff is the exact completion output, verifies the cycle-2 predecessor context, and records the exact-registry no-candidate evidence.

## What is real

The replay uses the repository-owned audited 1D heat-conduction solver, the repository action-registry contract, the real typed execution request format, the immutable research-action ledger, the existing pinned heat report verifier, the existing authorization reconstruction, and the authenticated epistemic-transition consumer.

The failing and corrected solver outcomes are generated by executing the same deterministic solver under two declared validation tolerances. Verifier success is never handwritten by the acceptance driver.

## What is deliberately absent

No empirical temperature measurement is created for this acceptance replay. When the numerical solver fails, physical comparison is blocked upstream. After numerical validity is restored, the system reports a real evidence gap instead of fabricating an observation.

The second-cycle bounded stop is not a claim that empirical evidence does not exist globally. It means only that the exact action registry configured and pinned for this replay does not contain a currently available `external_evidence_search` action. Planned or externally authorized acquisition remains future work.

## Claims this replay does not establish

A green replay does **not** establish material validity, process validity, empirical model validation, autonomous scientific truth, calibrated hypothesis probability, positive scientific closeout, or successful physical experimentation. The computational transition remains diagnostic and the target scientific-state fingerprint is required to remain unchanged when only graph-version bookkeeping or diagnostic edges are added.

## Fail-closed controls

The acceptance suite rejects at least the following substitutions:

- a different recursive-limits contract;
- a substituted source-discrepancy SHA in the candidate-match record;
- a substituted authenticated base graph;
- a substituted predecessor planning context even if re-hashed;
- stale cycle-1 plan reuse in cycle 2;
- caller attempts to provide a self-certified `verified_execution_record` through the public facade.

The public acceptance boundary additionally rechecks the exact execution-request bytes and registry SHA before using registry absence as bounded-stop evidence.

## CI visibility

The integration test is `tests/test_public_recursive_real_evidence_replay.py`. The standard CI workflow executes the complete pytest suite on Ubuntu and Windows, so any regression in this public composition path is a required PR check. Quality and Release Evidence and Autonomous Phase A-E remain required surrounding regression suites for the repository.

## Remaining research work

This replay closes an architectural composition uncertainty, not the empirical research frontier. The next scientifically valuable step is to register and authorize real external evidence-acquisition paths, acquire provenance-bound empirical artifacts, and then allow the recursive system to continue into independent physical comparison rather than stop at the evidence boundary.
