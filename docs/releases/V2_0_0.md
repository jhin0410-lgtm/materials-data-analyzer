# v2.0.0 - Platform Core and Controlled Execution

## Overview

v2.0.0 adds an additive platform layer around the existing v1.x case studies.
It introduces explicit registries, configuration validation, manifest-first
planning, controlled read-only execution for one trust verification adapter,
generic case-study lifecycle metadata, onboarding validation, and local-only
read-only platform reports.

This release does not replace existing case-study scripts or output schemas.
The v1.x workflows remain canonical.

## Why v2.0

The v1.x releases established a repeated pattern across Battery Archive,
Materials Project, Smart Factory / UCI SECOM, and Reliability / Backblaze:

- source provenance and acquisition boundaries
- schema/readiness audits
- local-only versus tracked compact artifact separation
- leakage-aware validation
- trust-boundary closeout
- clean snapshot testing

v2.0 turns that pattern into a common metadata and execution-control scaffold.

## Platform Architecture

The platform core adds:

- plugin registry
- adapter registry
- artifact registry
- validation policy registry
- trust policy registry
- execution policy registry
- case-study registry
- configuration validation
- dry-run planner
- run manifest lifecycle
- side-effect guard
- read-only report generator

The implementation lives under `src/platform_core/` and is exposed through
`python -m src.cli`.

## Plugin and Registry Model

Initial plugins:

- `battery_archive`: scaffolded / partially onboarded
- `materials_project`: dry-run ready
- `smart_factory`: dry-run ready
- `reliability`: dry-run ready with a controlled trust verification candidate

The registries reject duplicate IDs, dangling references, unsafe artifact
paths, tracked/local-only conflicts, and `production_ready` trust status.

## Manifest-First Dry Runs

Pipeline configs are JSON metadata only. They cannot define module paths,
callables, shell commands, credentials, raw-data permission, network
permission, model-training permission, or canonical overwrite permission.

Dry-run planning can write local manifests under `outputs/platform_runs/` when
explicitly requested.

## Controlled Execution

Only `reliability_trust_closeout` is executable in `verify` mode.

That path:

- reads registered tracked compact reliability trust artifacts
- verifies representative-model and prohibited-claim boundaries
- writes local verification outputs under `outputs/platform_runs/`
- checks protected compact artifact SHA values before and after execution

Materials Project, Smart Factory, Battery Archive, acquisition,
normalization, feature engineering, model training, raw-data reads, and
trust reruns remain disabled in the unified CLI.

## Case-Study Interface

v2.0 adds a generic lifecycle vocabulary:

```text
contract -> acquisition -> normalization -> readiness -> feature_build
-> validation -> trust -> closeout -> report
```

The interface records each case study's current state without pretending that
missing stages are complete.

## New-Domain Onboarding

The metadata-only onboarding validator checks whether a proposed future domain
has enough identity, target, time/group, artifact, validation, and trust-policy
metadata to be considered for later adapter work.

Passing onboarding validation does not prove scientific validity and never
grants execution permission.

## Read-Only Reporting

v2.0.5 adds JSON and Markdown platform reports from registries and tracked
compact artifacts.

The report engine:

- does not run acquisition, modeling, trust analyzers, or network calls
- does not read raw data, local analysis-ready tables, or row-level predictions
- does not recompute scientific metrics
- writes only local ignored outputs under `outputs/platform_reports/`
- records `scientific_recomputation_performed = false`

## CLI Commands

Examples:

```powershell
python -m src.cli list-plugins
python -m src.cli list-adapters
python -m src.cli list-case-studies
python -m src.cli validate-config configs/examples/reliability_trust_dry_run.json
python -m src.cli dry-run configs/examples/reliability_trust_manifest_dry_run.json --write-manifest
python -m src.cli execute configs/examples/reliability_trust_verify_run.json --mode verify
python -m src.cli preview-report --config configs/examples/platform_report_all_case_studies.json
python -m src.cli generate-report --config configs/examples/platform_report_all_case_studies.json
```

## Backward Compatibility

v2.0.0 preserves:

- `src/process_data.py`
- existing scripts under `scripts/`
- existing case-study contracts and docs
- existing processed compact artifact schemas
- v1.x tests
- raw/local-only artifact policy

## Security Boundaries

The platform layer avoids:

- `eval`
- `exec`
- arbitrary imports from user config
- subprocess or shell execution in platform operations
- network access
- raw-data reads
- model fitting
- credential logging
- host/user/home path exposure
- canonical tracked output overwrite

## Tests and CI

Release audit validation used:

- full local test suite: `516 passed, 1 skipped`
- direct pytest with repository-local basetemp: `516 passed, 1 skipped`
- clean tracked snapshot: `516 passed, 1 skipped`
- feature branch GitHub Actions: green before merge

The skipped test is an existing platform artifact-resolver symlink/path-policy

## Known Limitations

- This is still a CLI-first scaffold, not a production orchestration service.
- Only reliability trust verification is executable.
- Other adapters remain dry-run or metadata-only.
- There is no automatic full-pipeline execution.
- There is no dashboard, UI, PDF report, or HTML report.
- Report generation summarizes existing artifacts and does not perform
  scientific analysis.

## Migration Notes

No migration is required for existing v1.x workflows. Existing scripts and
case-study commands remain the canonical way to regenerate case-study
artifacts.
