# v2.7.0 - Evidence Governance and Cross-Repository Integration

Release date: 2026-07-28

## Overview

v2.7.0 closes the complete development scope accumulated after v2.4.0 as one
additive public release. It combines:

- versioned compatibility and retrieval-reproducibility evidence;
- a leakage-safe Battery forecast benchmark with the negative result preserved;
- the complete v2.6 external-evidence line through its checksum-bound closeout;
- schema `1.0` cross-repository characterization handoff;
- pinned public DWCNT, RWGS, four-carbon-material, and NIST workflows;
- a representative NIST process-characterization workflow that stops before
  unsupported modeling or optimization;
- public repository, citation, and release-governance hardening.

This release is an evidence and interoperability milestone. It is not presented
as a successful predictive-model release or an autonomous engineering system.

No missing source snapshot, timestamp, API client, license, calibration, or
measurement-uncertainty metadata is inferred.

## Battery forecast benchmark

The release includes a leakage-safe five-cycle capacity-retention benchmark with:

- battery-disjoint GroupKFold validation;
- train-only preprocessing;
- persistence and fixed Ridge baselines;
- deterministic prediction and diagnostic checksums;
- preview, run, and validate CLI commands.

The actual result is **Unsupported** as a predictive-improvement claim:

- Ridge pooled MAE: `4.1537`;
- persistence pooled MAE: `3.4256`;
- Ridge improves on 13 of 33 evaluated batteries.

Deterministic diagnostics do not identify a single exclusion that reverses
persistence superiority. No feature retuning, clipping, target redefinition,
battery exclusion, or model-family search was used to manufacture a positive
result. The release makes no zero-shot, SOH, RUL, lifetime, mechanism, or
engineering-decision claim.

## Cross-repository characterization handoff

The data repository consumes schema `1.0` bundles from the independently
installable `materials-characterization-analyzer` repository. The consumer
validates:

- explicit `sample_id` identity rather than row order;
- bundle paths, sizes, hashes, and exact long-format columns;
- finite numeric values and semantic feature identity;
- source and preprocessing provenance;
- sample context and external process-table identity;
- deterministic reports and manifests;
- one-to-one joins without direct internal imports.

Pinned public workflows cover:

- DWCNT multimodal evidence;
- RWGS XRD/EDS while preserving the blocked SEM quantitative result and
  unresolved Ni context;
- four carbon material classes without treating class differences as controlled
  process effects;
- NIST AM-Bench optical-metrology features joined to consumer-owned process
  conditions.

These cases remain **Diagnostic**. They do not establish phase identity,
chemical state, identical aliquots, mechanism, causality, prediction,
optimization, or engineering-release suitability.

## Representative NIST AM-Bench workflow

A one-command workflow now performs:

```text
verified NIST source-table case
-> sample-ID and provenance integration
-> artifact integrity closeout
-> process-design identifiability audit
-> bounded minimum next-experiment plan
-> Diagnostic scientific closeout
```

The current case contains 10 traces and three coupled power-speed conditions.
The design has 50% coverage of the observed 2 x 3 grid and returns
`not_ready_for_predictive_or_causal_modeling`. The bounded recommendation is to
complete the three missing factorial combinations with at least three traces per
condition, subject to machine, calibration, safety, and experimental-purpose
review. No response model or process optimum is generated.

Official commanded-to-actual laser-power mappings and the AMMT laser-spot-size
correction are preserved as provenance. They do not silently change active
process inputs or create an inferred volumetric-energy-density variable.

## Security and artifact policy

The release does not intentionally include credentials, private datasets, raw
archives not approved for redistribution, generated `outputs/`, local absolute
paths, arbitrary serialized Python objects, or local row-level model predictions.
External datasets, publications, standards, and software retain their own
licenses and citation requirements.

## Validation boundary

Release validation covers software behavior, deterministic artifacts, metadata
consistency, and tracked compatibility evidence. It does not establish source
truth, instrument calibration, measurement uncertainty, sample comparability,
causal validity, mechanism validity, predictive generalization, optimization
readiness, or production engineering suitability.
